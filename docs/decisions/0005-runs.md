# 5. Store each run in its own folder

**Status:** Accepted

## Context

convy 0.1 wrote a header and a line per attempt to `results/runs/<agent>/<start>.jsonl`.
It saved scenario IDs and claims. It could not detect an edit to the scenario instructions,
explain which claim failed, or reliably distinguish a completed run from a stopped run.

## Decision

A run plays a set of scenarios against one agent build, with `k` attempts per scenario.
For example, `convy run a b` creates two runs.

Each run has a folder under `results/<agent>/<id>/`. The ID combines the start time with four
random hex digits. The folder contains:

- `run.json` records the format, specification and status. convy replaces it atomically using
  a temporary file. The specification includes the scenario definitions, agent version, model
  names, run settings, convy version and SHA-256 hashes of the agent file and `models.py`.
- `attempts.jsonl` gains one line per completed attempt. The judge decides each claim
  individually. An agent failure ends the attempt before judging.
- `run.lock` lets one process at a time play the run on file systems that support locking.
  The operating system releases the lock when the process exits.

The status starts as `running` and changes to `finished` or `interrupted`. A process that
dies can leave the status at `running`. Resume uses the saved scenarios and scoring settings.
It checks file hashes, versions and model names before running missing attempts. The project
can change its [request limits](0007-participant-limits.md) for resume.

**Compatibility.** The current reader accepts format 9. Older runs lack fields needed for
[scoring](0012-claim-scoring.md) or [tool counts](0013-tool-invocations.md). Use the version
that wrote the run, open its standalone HTML report, or record a new run.

## Alternatives and consequences

- A single JSON Lines file would be easy to send, but a final status line would end up in the
  middle after a resume. A shared SQLite database would require separate tools to copy or remove
  an individual run.
- Resuming the most recent run would be ambiguous when multiple agents or terminals are active.
  Supplying the run ID identifies the intended run.
- The CLI uses the scenario snapshot to identify unchanged scenarios for comparison. The
  [workspace](0014-runs-workspace.md) links each scenario to its recorded attempts.
- Resume cannot detect changes inside an imported module or a remote service. Python callers
  must also ensure that the `Bench` passed to `RunJournal.play` matches the recorded specification.
